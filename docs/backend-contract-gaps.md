# Backend contract gaps

Places where `contracts/openapi.json` (backend `920ff6a`, 2026-10-22) and the documents
disagree, found from the client side. This repository never modifies `../moyi-backend`;
each gap is written here for a backend session to fix, together with how the client copes
until then. Checked with `jq` against the contract, not only read.

| # | Gap | Doc says | Contract says | Client meanwhile |
|---|---|---|---|---|
| 1 | `POST /auth/login` has no `401` | `06` §3.1: every refusal is `401 INVALID_CREDENTIALS` | responses `200, 400, 422, 429, 500` | Decodes `application/problem+json` on **any** non-2xx status, declared or not |
| 2 | `POST /auth/refresh` has no `401` | `06` §3.1: `401 TOKEN_REUSE_DETECTED` / `REFRESH_TOKEN_INVALID` | responses `200, 400, 422, 429, 500` | Same as 1; only these two codes end the session |
| 3 | `POST /auth/verify-email` has no `410` | `06` §3.1: `410 VERIFICATION_TOKEN_EXPIRED` (expired or already used) | responses `200, 400, 422, 429, 500` | Same as 1; switches on `code`, not status |
| 4 | `LoginResponse` declares no `required` | the four fields are always present | `required` absent, so every field is nullable in generated code | Repository mapper treats a missing token as a serialization error; success is checked before decoding the body |
| 5 | `UserResponse` declares no `required` | `id`, `email`, `displayName`, `emailVerified`, `status` always present | `required` absent | Same as 4 |
| 6 | `ProblemDetail` has no `traceId` | `06` §2: every error body carries `traceId` | properties `code, detail, errors, instance, status, title, type` | Not surfaced; logged if present via raw JSON |
| 7 | `servers[0].url` is `http://localhost` and paths carry `/api/v1` | `06` §1: base URL ends in `/api/v1` | server has no path; every path starts `/api/v1` | Config keeps the `…/api/v1` form; one tested function derives the origin for the generated client |
| 8 | `DeviceRequest.platform` is a `pattern`, not an `enum` | `ANDROID \| IOS \| WEAR` | `pattern: "ANDROID\|IOS\|WEAR"` | Generated as `String`; the client sends constants |
| 9 | `RegisterRequest.over18` is optional | sign-up requires the 18+ confirmation | not in `required` | Sent as the consent box's value; the action stays disabled until it is checked |
| 10 | `DayResponse.partnerEntry` / `TodayResponse.partnerEntry` is a `oneOf` with a `status` discriminator whose mapping sends three statuses to `EntryResponse` | `06` §3.4: the partner's entry is locked, revealed or erased, told apart by `status` | OpenAPI Generator 7.26 (`kotlin`/`multiplatform`) emits a sealed class with **no subclasses**, so every non-null `partnerEntry` throws on decode (spike, 2026-10-27, MockEngine). kotlinx polymorphism cannot map several discriminator values to one class either | Mapped since the daily-loop wiring: `schemaMappings` sends `DayResponse_partnerEntry` (the raw inline name) to `com.moyi.app.api.wire.PartnerEntryWire`, the one hand-written file in `:shared:data:api`. It declares no field of its own: it reads `status` and decodes the **generated** `EntryResponse`, `LockedEntryResponse` or `ErasedEntryResponse`, exactly as `discriminator.mapping` says; any other status is a decode failure, never a guess. Delete it with the fix below |
| 11 | **Backend ask, not a contract gap**: strict rotation plus a lost refresh response gives a false reuse alarm | ADR-0021: a refresh token presented twice revokes the family and emails the person; no grace window | `POST /auth/refresh` rotates on receipt; nothing lets a client retry the same refresh safely | When the answer to a refresh is lost after the request was sent (a read or request timeout, a reset connection, the app killed), the client keeps R1, and its next refresh trips `TOKEN_REUSE_DETECTED`: a legitimate user signed out everywhere and emailed. The client cannot fix this. It classifies such failures as ambiguous and logs them, and any reuse that follows, under the Kermit tag `SessionRefreshAmbiguous` (docs/session.md, "The lost response"), so the rate can be measured. Options for the backend: **(a)** an `Idempotency-Key` header on `/auth/refresh` that replays the same R2 for a retried R1 within N seconds; **(b)** a same-device grace window of a few seconds; **(c)** accept the risk. Needs an owner ruling and an amendment to ADR-0021. Note for (a): the backend already has an `Idempotency-Key` mechanism (`IdempotencyConfiguration`, first used on `POST /bonds/{bondId}/entries`, read at backend `ce41f22`), so the fix could reuse it |
| 12 | `GET /meta/legal` is missing | `06` §3.7: "Current Terms/Privacy versions + URLs" | no `/meta/*` path at all (checked with `jq`, 2026-10-29) | The Terms and Privacy links open in-app (D8) from build configuration, `moyi.termsUrl` / `moyi.privacyUrl`; unset, they do nothing. No published legal page exists yet either, so the URLs are owed whichever way they arrive. Still missing in the live backend contract at `16c235a` (2026-11-05); filed as [moyi-backend#128](https://github.com/Ayodeji97/moyi-backend/issues/128) |
| 13 | The bond and invite responses declare no `required`: `BondResponse`, `BondsResponse`, `InviteResponse`, `InviteDetailResponse`, `InvitePreviewResponse`, `MemberResponse`, `MeResponse` | `BondResponse` is "the one shape every bond endpoint returns" (backend `BondResponse.kt`); its non-null Kotlin properties are always present | `required` absent on all seven (checked with `jq`, 2026-10-29), so every field is nullable in generated code. Their enums (`status`, `type`, `bondType`, `role`) are closed: a value this build does not know fails the decode | The repository mappers (`BondMappers.kt`) treat a 2xx missing a field the app routes on (`id`, `name`, `type`, `status`; an invite's `id`, `code`, `link`; a preview's three fields) as `DataError.Network.Serialization`, and one malformed bond fails the whole list, so a partial list can never send a person with a bond back through onboarding. An unknown enum value is the same error, never a crash. `InviteResponse` and `InviteDetailResponse` are the same four fields under two names; both are mapped |
| 14 | `CreateBondRequest.type` is a free `string` | `06` §3.3: `type` is one of `COUPLE`, `FRIENDS`, `FAMILY`, `PARENT_CHILD` (the backend validates exactly those, `ValidBondType`) | `"type": {"type": "string"}` with no `enum`, while `BondResponse.type` has one | Generated as `String`; the client sends the domain `BondType`'s name, so only those four can be sent |
| 15 | `POST /auth/reset-password` has no `410` | `06` §3.1: `410 PASSWORD_RESET_TOKEN_EXPIRED` (expired, or already used), mirroring verification | responses `200, 400, 422, 429, 500` (checked against the vendored contract, 2026-11-05); the code itself is in `ProblemDetail.code`'s enum, so `ApiErrorCode.PASSWORD_RESET_TOKEN_EXPIRED` exists | Same as 1 and 3: the problem body is decoded on any non-2xx status and the screen switches on `code`, never the status (`AuthErrorMapper.resetTokenError`) |
| 16 | **Missing endpoint**: account deletion, `POST` / `DELETE /me/deletion-request` | `06` §3.2: "`202`, 14-day cancellation window" and "Cancel"; FR-008 (MUST); `states.md` §9 "Account deletion"; scheduled for Phase 5 (`15`), not deferred by any ADR | Only `GET /me` under `/me` in the live backend contract at `16c235a` (2026-11-05) | The account screen does not offer deletion, rather than offering a control that does nothing. Filed as [moyi-backend#125](https://github.com/Ayodeji97/moyi-backend/issues/125) |
| 17 | **Missing endpoint**: data export, `POST /me/export` and `GET /me/export/{id}` | `06` §3.2: "`202` → async; email + push when ready" and "Signed download URL, 24h TTL"; FR-009 and FR-094 (MUST); `states.md` §9 "Retained access"; ADR-0035 question 2, owner's ruling: "An export that works before launch is a condition of M5" | No export path in the live backend contract at `16c235a` | "Export your archive" is not offered on any of the five screens that draw it. The block confirm does not promise an export it cannot make. Filed as [moyi-backend#126](https://github.com/Ayodeji97/moyi-backend/issues/126) |
| 18 | **Missing endpoint**: report the other **member** (FR-100's member half) | `06` §3.7 `POST /reports {targetType, targetId, …}`; `26` §1 and §4: a report targets "a member or a single entry"; ADR-0053 open question 6: "Reporting the member … not built" | Only `POST /entries/{entryId}/report` in the live backend contract at `16c235a` (ADR-0053; not yet in this repo's copy) | `Report · choose target` shows the entry row only; the member row is not drawn. Filed as [moyi-backend#127](https://github.com/Ayodeji97/moyi-backend/issues/127) |
| 19 | **Missing endpoint**: `POST /support/messages` | `06` §3.7: "FR-102. `{subject, body}` → creates an admin-visible ticket + acknowledgement email. 5/day/user"; `06` §4 bucket `support:create`; FR-102 (MUST) | No `/support/*` path in the live backend contract at `16c235a` | Any "Contact support" affordance opens the system mail composer to the configured support address. That is a link, so the client is not blocked, but it does not meet FR-102's ticket and acknowledgement. Filed as [moyi-backend#129](https://github.com/Ayodeji97/moyi-backend/issues/129) |
| 20 | **Backend ask, not a contract gap**: verification and password reset should take a **short code the person types** (for example 6 digits), not a copied link (owner request 2026-11-06, PR 30 smoke test) | ADR-0015 and ADR-0018 to 0025: the emailed link carries a long single-use token; the link points at the website (`localhost:3000` locally), where opening it fails, so the only working path is copying the link and pasting it into the app | `POST /auth/verify-email` and `POST /auth/reset-password` take only that long token from the link | The paste-the-link flow: the paste field accepts the token or the whole link. The reset "Check your email" line says so explicitly (interim copy, owner ruling 2026-11-06). The existing code field can take a short code once the contract has it. What the backend needs: **(a)** the email carries a code; **(b)** both endpoints accept it **with the email**, since a short code alone is not unique; **(c)** per-code attempt limits and an expiry, because a 6-digit code is guessable; **(d)** rate limiting on both endpoints; **(e)** an amendment to the auth ADRs (0015, 0018 to 0025). Complementary option: Universal Links (iOS) and Android App Links, so the emailed link opens the app directly; that needs `apple-app-site-association` and `assetlinks.json` served from getmoyi.app, outside this repository |
| 21 | `StreakResponse` and `StreakDayResponse` declare no `required` | states.md §7a: every field is sent (`current`, `longest`, `freezesAvailable`, `freezeProgress`, `strictMode`, `totalCompleteDays`, `lastCompleteDate`, `days`) | no `required` on either schema (checked with `python3 -I`, 2026-11-06) | Generated nullable. A missing `current`, `longest`, `freezesAvailable`, `strictMode`, `days`, or a cell without `date` or `status`, fails as Serialization (the Generic error), never drawn as 0. `freezeProgress` and `totalCompleteDays` default to 0: not drawn |
| 22 | The length of the run that just ended is not sent | states.md §7 / Figma 401:160: "Your streak ended at 21 days. That is 21 days of showing up." | `current` is 0 and `longest` is the longest ever, not the last run (states.md §7a, gap) | The ended line leaves the number out (PROPOSED "Your streak ended. No rest days were left."). The client does not count it from the cells: the streak is server-authoritative |
| 23 | A `FROZEN` cell does not say why | states.md §7: "Yesterday slipped by. We used a rest day. One left." | `FROZEN` is a rest day used **or** a date a timezone change stepped over (states.md §7a, gap); nothing tells them apart | Yesterday `FROZEN` shows the drawn rest-day line, which is wrong for the timezone case |

Suggested backend fix for 21: the same `required` marking. For 22: a `lastRunLength` (or `endedAt`) field. For 23: a reason on the cell, or copy that fits both.
| 24 | `409 TIMEZONE_CHANGE_TOO_SOON` carries its date only in `detail` prose | `states.md` §8: "The month's refusal is a `409` with a date in it … a date, because a countdown framed as a deadline is the urgency `copy.md` bans"; `06` §3.3: "with the date in the detail" | `ProblemDetail` has no field for it; its own description says "`detail` is prose and may change" (checked with `python3 -c json`, 2026-11-06). The backend writes an English sentence (`BondErrors.kt`, read only) | The client does not parse prose and shows no date: "The shared time zone changed less than 30 days ago, so it cannot change again yet." (PROPOSED). `BondResponse` has no "last changed" field either, so the date cannot be worked out. Fix: an `allowedFrom` date (or the bond's `timezoneChangedAt`) as a typed `ProblemDetail` extension or `BondResponse` field; the client then fills `{date}` in its own words |

Suggested backend fix for 13 and 14: the same `required` marking, and `@Schema(allowableValues = …)` (or a typed
`BondType` with the 422 kept) on `CreateBondRequest.type`.

Suggested backend fix for 1–3, 15 and 6: declare the 401/410 responses with the
`ProblemDetail` schema on those operations, add `traceId` to `ProblemDetail`, and mark the
always-present response fields `required` (springdoc: non-null Kotlin properties, or
`@Schema(requiredMode = REQUIRED)`). That is a contract change, so it carries the
backend's `breaking-api-change` review.

Suggested backend fix for 10: give each partner-entry variant its own schema and one
discriminator value (`LOCKED`, `REVEALED`, `ERASED`, and so on), so the generated sealed
class has one subclass per value and the client needs no hand-written serializer.
